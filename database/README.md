# CampusConnect Phase 3 database scripts

These Oracle scripts are manual setup artifacts. They are not invoked by Maven, Tomcat, or the application. They do not create/drop users, drop existing objects, or overwrite existing rows.

## Before running

- Confirm the target database is `FREEPDB1` and the connection uses the existing `CAMPUSCONNECT` account and external JDBC configuration.
- The default tablespace was confirmed with the read-only query `SELECT default_tablespace FROM user_users`; it returned `USERS`.
- `00_schema_permissions.sql` is the only script to run as `SYSTEM`. It checks that the current PDB is `FREEPDB1` and that `CAMPUSCONNECT` still defaults to `USERS`, then grants only `CREATE SESSION`, `CREATE TABLE`, and `CREATE VIEW`, with a 25 MB quota on `USERS`. It does not grant `DBA`, `UNLIMITED TABLESPACE`, or `CREATE SEQUENCE`.
- Connect as `CAMPUSCONNECT` to `FREEPDB1` for the remaining scripts. The schema uses Oracle identity columns (`GENERATED BY DEFAULT ON NULL AS IDENTITY`) for all generated IDs, so `02_sequences.sql` is intentionally explanatory and creates no sequences. Identity columns require Oracle Database 12c or later.
- Use SQL Developer's **Run Script** (F5) or SQL*Plus so `WHENEVER SQLERROR`, `PROMPT`, and `DBMS_OUTPUT` work as intended.

## Execution order

1. As `SYSTEM` in `FREEPDB1`, run `00_schema_permissions.sql`.
2. Reconnect as `CAMPUSCONNECT` in `FREEPDB1`.
3. Run `01_tables.sql`.
4. Run `02_sequences.sql` (documentation only; no DDL is issued).
5. Run `03_views.sql`.
6. Run `04_sample_data.sql` once if the demo rows are wanted.
7. Run `05_verify.sql`.
8. After Phases 1–6 and the Phase 7 backend are installed, run the additive `08_phase7_scoring.sql` migration as `CAMPUSCONNECT` in `FREEPDB1`. The application migration was applied and verified through the external JDBC configuration; this file is the repeatable deployment record. Do not rerun `04_sample_data.sql`.

## Schema and registration rules

- A user has one `role_code`: `STUDENT`, `ORGANIZER`, `JUDGE`, or `ADMIN`. No password or login material is stored in this Phase 3 schema.
- Events point to an owner user. Java services must check that the owner is an active `ORGANIZER` when creating or changing an event.
- A registration has exactly one subject: an individual `participant_user_id` or a `team_id`. The check constraint enforces that shape; Java services must require its registration type to match the event's `participation_mode`, and require active `STUDENT` users/members.
- Filtered unique indexes prevent a second individual registration for the same event/user or a second team registration for the same event/team; unique constraints prevent duplicate team membership and duplicate score submissions for the same registration/criterion/judge. The filtered indexes ignore rows of the other registration subject type so multiple individual or team registrations can share an event.
- Because those uniqueness rules include cancelled registrations, Java services should reactivate an existing cancelled registration when policy permits instead of inserting a second row for that same event and subject.
- Java services must check registration windows, event publication/status, seat capacity and waitlist transitions, team size and eligibility, and freeze or revalidate team membership after registration. Capacity/size checks need transaction-safe locking to avoid concurrent overbooking.
- Java services must validate that event owners, participants, and assigned judges have the required roles. The score foreign keys already require the judge to be assigned to the score's event and the registration and criterion to belong to that same event.
- Java services must reject scores above the criterion's `max_points`, require the event's criterion weights to total 100 before finalizing results, and decide when results become final. The results view averages multiple judges per criterion, applies each criterion's percentage weight, and ranks the registrations.
- Phase 7 keeps the existing `V_CC_EVENT_RESULTS` formula unchanged. The additive scoring lifecycle migration adds event scoring-window, result-finalization, and result-publication timestamps. Judges score only confirmed registrations during the inclusive configured window; finalization requires every assigned judge to score every criterion for every confirmed registration and weights to total exactly 100. Public results are exposed only after publication. Existing complete `COMPLETED` events are marked published by migration without changing their scores or calculated results.
- Email case normalization and any rule preventing the same student from representing multiple teams in one event require Java service validation.

## Expected verification output

After the scripts and demo data are successfully applied, `05_verify.sql` should report:

- 8 CampusConnect tables and both views.
- At least 30 enabled and validated primary, foreign, unique, and check constraints; it also checks the named score relationship and duplicate-prevention constraints.
- Two mode-consistent demo registrations, two members in `DEMO Team Alpha`, and two scores linked to their registrations, event criteria, and assigned judge.
- `DEMO-TEAM-2026` with weighted score 85 and `DEMO-IND-2026` with weighted score 90.

## If a script fails

- Stop at the first error and keep the full SQL Developer Script Output or SQL*Plus error text.
- Oracle commits DDL implicitly. If `01_tables.sql` fails part way through, inspect `USER_TABLES`, `USER_INDEXES`, and `USER_CONSTRAINTS`, then apply only missing/corrected statements after confirming the partial state. Do not drop objects or rerun the entire DDL script blindly.
- `03_views.sql` uses `CREATE OR REPLACE VIEW`; it can be rerun to replace either view without changing table data.
- The inserts in `04_sample_data.sql` are one transaction with a single commit at the end. On an error the block rolls back all sample inserts. Oracle identity values may have gaps after a rollback. If the script already succeeded, do not rerun it; unique constraints will reject duplicate demo keys and the block will roll back.
- `05_verify.sql` is read-only. If it reports an error, correct the reported prior setup/data issue and run verification again; do not alter data just to silence a failed check.

The scripts have been authored but **not executed**. Database object and sample-data verification remains pending until you run them against `FREEPDB1`.

## Phase 8 admin controls

`09_admin_controls.sql` is an additive, run-once migration for `CC_ADMIN_CONTROL` and `CC_ADMIN_AUDIT`. It was applied through the application's `DBConnection` after verifying `SESSION_USER=CAMPUSCONNECT`, `CURRENT_SCHEMA=CAMPUSCONNECT`, `CON_NAME=FREEPDB1`, and `CC_USERS`. The audit constraints were verified enabled and validated; both audit indexes were valid; the guard row exists. Do not run this migration as SYSTEM or rerun it blindly. If applying it in another environment, inspect existing objects first and continue only with missing statements.
